DR. MARIO 99 - COMPREHENSIVE PROJECT DOCUMENTATION
==================================================

OVERVIEW
========
Dr. Mario 99 is a modern web-based implementation of the classic Dr. Mario puzzle game, featuring both single-player and real-time multiplayer modes. Built with vanilla JavaScript, Web Components, and Socket.IO, it provides an authentic Dr. Mario experience with enhanced multiplayer capabilities.

KEY FEATURES
============
- Classic Dr. Mario gameplay mechanics
- Real-time multiplayer with room-based matchmaking
- Synchronized virus positions and pill colors across players
- Competitive damage system between players
- Responsive design with modern web technologies
- Seamless single-player to multiplayer transition

TECHNICAL ARCHITECTURE
======================

CORE TECHNOLOGIES
-----------------
- **Frontend**: Vanilla JavaScript (ES6+), Web Components, CSS3
- **Backend**: Node.js with Express and Socket.IO
- **Communication**: WebSocket-based real-time multiplayer
- **Storage**: LocalStorage for high scores and game state
- **Rendering**: CSS positioning (no Canvas required)

UNIFIED FILE STRUCTURE
----------------------
The project has been consolidated from parallel Player 1/Player 2 files into a unified architecture:

```
public/
├── index.html              # Main HTML with Socket.IO integration
├── scripts/
│   ├── Game.js            # Unified game controller (supports both players)
│   ├── Board.js           # Unified game board logic
│   ├── Shape.js           # Unified game pieces (pills, viruses)
│   ├── components.js      # Game constants and enums
│   └── script.js          # Game initialization and dynamic loading
├── styles/
│   └── style.css          # Game styling and responsive design
└── img/                   # Game assets (pills, viruses, backgrounds)

server.js                  # Node.js server with Socket.IO
```

CORE COMPONENTS
===============

1. SERVER.JS - MULTIPLAYER BACKEND
----------------------------------
**Purpose**: Handles all multiplayer communication, room management, and game data synchronization.

**Key Features**:
- Room-based multiplayer with unique 4-character codes
- Seeded random number generation for synchronized game data
- Real-time communication between players
- Game state management and synchronization

**Critical Functions**:
```javascript
// Room Management
socket.on('createRoom', (roomCode) => { ... })
socket.on('joinRoom', (roomCode) => { ... })

// Game Data Generation
generateVirusPositions(roomCode)    // Creates unique virus layouts per room
generateRandomList(roomCode)        // Creates unique pill color sequences per room
generateNewGameData(roomCode)       // Orchestrates data generation and storage

// Player Communication
socket.on('sendDamage', (data) => { ... })
socket.on('updatePoints', (data) => { ... })
```

**Synchronization System**:
- Each room gets unique virus positions based on room code + timestamp
- Each room gets unique pill color sequences for fair gameplay
- Data is generated once per room and shared with all players
- Seeded random generation ensures reproducibility

2. GAME.JS - UNIFIED GAME CONTROLLER
-----------------------------------
**Purpose**: Main game orchestrator that manages the entire game lifecycle for both single-player and multiplayer modes.

**Key Features**:
- Dynamic player number support (1 or 2)
- Multiplayer state management and synchronization
- Game lifecycle management (start, level progression, game over)
- Socket.IO integration for real-time communication
- Shared game data initialization

**Critical Functions**:
```javascript
constructor(playerNumber = 1)           // Supports both players
initializeWithSharedData()              // Syncs with server data
setupSocketListeners()                  // Handles multiplayer events
nextStage()                             // Level progression
endGame()                               // Game over handling
showWinScreen() / showOpponentWinScreen() // Victory/defeat displays
```

**Multiplayer Integration**:
- Receives shared game data from server
- Synchronizes virus positions and pill colors
- Handles damage transmission between players
- Manages victory/defeat scenarios

3. BOARD.JS - UNIFIED GAME LOGIC
--------------------------------
**Purpose**: Core game mechanics including pill movement, virus management, scoring, and multiplayer damage system.

**Key Features**:
- 8x17 game grid management
- Pill movement, rotation, and placement
- Virus spawning and elimination
- Line clearing mechanics (3+ matching colors)
- Gravity system for falling pieces
- Multiplayer damage system
- Score tracking and display

**Critical Functions**:
```javascript
constructor(game, level = 0, score = 0, playerNumber = 1)  // Dynamic player support
nextFrame()                                                // Main game loop
spawnViruses()                                            // Places viruses at game start
clearIfNeeded()                                           // Checks for line clears
useGravitation()                                          // Makes pieces fall
hurt()                                                    // Receives damage from opponent
spawnRandomDot()                                          // Creates falling damage pieces
```

**Game Mechanics**:
- Pills fall from top and can be rotated/moved
- Matching 3+ same colors in row/column clears them
- Clearing lines eliminates viruses of matching colors
- Multiplayer damage sends falling pieces to opponent

4. SHAPE.JS - UNIFIED GAME PIECES
---------------------------------
**Purpose**: Defines and manages all game pieces including pills, viruses, and their interactions.

**Key Features**:
- Pill class: Two-colored capsules with rotation mechanics
- Virus class: Single-colored targets for elimination
- ShapePiece class: Individual components of shapes
- Movement validation and collision detection
- Shared pill color system for multiplayer fairness

**Critical Functions**:
```javascript
// Pill Management
class Pill extends Shape {
    constructor(board, color1, color2)  // Dynamic positioning
    createPieces(color1, color2)        // Creates pill components
}

// Color System
randomColor()                           // Uses shared server data
updateNumber()                          // Advances through color list
```

**Synchronization Features**:
- Uses server-provided pill color sequences
- Ensures both players get identical pill colors
- Position tracking for fair color consumption
- Fallback to default colors if server data unavailable

**Purpose**: Centralized configuration for all game constants, colors, and timing.

MULTIPLAYER SYSTEM
==================

ROOM MANAGEMENT
---------------
- **Room Creation**: Players generate unique 4-character room codes
- **Room Joining**: Second player joins using the room code
- **Data Generation**: Server creates unique game data for each room
- **Synchronization**: All players in a room receive identical game data

GAME DATA SYNCHRONIZATION
-------------------------
**Virus Positions**:
- Generated using seeded random number generator
- Seed based on room code + timestamp
- Ensures unique layouts per room
- Synchronized across all players

**Pill Colors**:
- Generated using same seeded system
- 100-color sequence per room
- Consumed in order for fairness
- Prevents color prediction/cheating

**Damage System**:
- Clearing lines sends damage to opponent
- Damage appears as falling colored pieces
- Pieces become viruses when they land
- Creates competitive pressure

REAL-TIME COMMUNICATION
-----------------------
**Socket.IO Events**:
```javascript
// Room Management
'createRoom'     // Create new game room
'joinRoom'       // Join existing room
'gameReady'      // Game starts when 2 players join

// Gameplay
'sendDamage'     // Send damage to opponent
'updatePoints'   // Sync score updates
'gameOver'       // Notify game end
'opponentWin'    // Opponent victory notification
```

MULTIPLAYER ROOMS AND FREE PLAY (PARTIES)
-----------------------------------------
Up to 8 players, each on their own screen and running their own board, so
nobody plays with lag (`public/scripts/partyClient.js`; server: PARTIES in
`server.js`). The old two-player CREATE ROOM / JOIN ROOM is gone from the menu
(its server code still serves AI MODE).

- **MULTIPLAYER** (under SINGLE PLAYER): YOUR NAME (remembered), then CREATE
  ROOM - you're the host - or JOIN ROOM with the 4-letter code. The room shows
  the code and an invite link (`/?party=CODE` opens straight into joining).
  The host sees ✕ by every player (partyKick, also mid-match: that player is
  out), ADD CPU (its board runs on the host's screen), VIRUSES, and START
  MATCH (2+ players). Everyone else sees "Waiting for HOST to start". If the
  host leaves, the next player becomes host
- **In a match**: my board on the left (or under the others on a phone), the
  others' boards on the right, drawn from what their screens send
  (partyBoard: the changed cells every 200 ms, a full picture every 2 s, and
  viruses/score). "▸ YOUR TARGET" and "⚔ ATTACKING YOU" label the boards. A
  clear of 4+ sends junk to my target, the next player still in round the
  circle (partyAttack -> partyJunk to whoever runs that board). A full bottle
  is out (partyOut); clearing your board wins (partyCleared); the last one
  left wins (partyOver). Keyboard, the touch buttons and a controller all work
- **On a phone** (`layoutPhone`, `body.phone-play`, also in landscape): only the
  bottle shows (a clip-path on the board, `BOTTLE`), with VIRUS, SCORE, LEVEL,
  NEXT and HOLD beside it (`#partyHud`, `updateHud`), the other players as a strip
  above and large thumb buttons below: move and drop on the left, turn and hold
  on the right. A tap on any button is one step however long the thumb stays
  down; a held move repeats after a moment, a held DROP keeps dropping
- **Results**: standings; the host gets PLAY AGAIN and BACK TO THE ROOM,
  everyone else waits for the host; LEAVE
- **Dropping out**: a player who loses the connection mid-match has 8 s
  (PARTY_GRACE_MS) to come back - their page rejoins by itself
  (partyJoin with their clientId) - before they're out
- **Phone screen** (MULTIPLAYER and FREE PLAY, `layoutPhone` in partyClient.js, `body.phone-play`): only the
  bottle shows (a clip-path over the board), with the numbers beside it (#partyHud), the other players in a
  strip above and six big buttons below (in landscape, either side). The buttons are real presses
  (setupTouchControls in index.html): a tap is one step, held moves repeat, held DROP keeps dropping that pill
- **FREE PLAY** first asks how you want to play, like Single Player (touch or keyboard, phone, Pro Controller).
  A phone pairs through a one-phone TV room that only passes its presses on (`pairOnly`, `tv.forFreePlay`)
- **FREE PLAY**: a 100-player match, last one standing. Everyone pressing it within 1.5 s (FREE_WAIT_MS;
  straight away if nobody else is free) shares one, and opponents with ordinary names fill the other seats.
  They aren't boards: royale.js keeps a few numbers for each on the server, ticked once a second (royaleTick), so
  a phone only runs its own board. Each attacks the next one still in, round the circle, as usual; real players'
  boards go only to the two players who show them. The screen shows how many are left, a square per player, and
  my target and attacker. Clearing your bottle is the next level and a big attack, not a win. Out: your place
  at once. Last one left: the VICTORY screen. `node tools/royale-sim.js` shows how long a match lasts (about 6
  minutes); ROYALE_SPEED=20 on the server runs it faster for testing. FIND ANOTHER MATCH looks again
- **Game logs**: each screen logs its own boards (mode `party`), so a
  multiplayer match has one log per player, replays included

TV ROOM (PHONES AS CONTROLLERS)
-------------------------------
The computer (usually on a TV) shows every player's board; each player scans a
QR code and uses their phone as the controller. 1 to 20 players. The TV side is
`public/scripts/tvHost.js`, the phone is `public/controller.html`, the server
side is the TV ROOM section of `server.js`.

- **Start**: "Start TV Room" on the computer opens a lobby with a QR code.
  `/tv` (e.g. https://dr-mario99.onrender.com/tv) does it by itself: the
  server redirects to `/?tv=new`, which opens a new room on load
- **Joining**: The QR code links to `/controller.html?room=CODE&player=N` for
  the next open slot (1-8), on the computer's Wi-Fi address when the page is
  opened on localhost (`os.networkInterfaces()`), otherwise the site's own
  address. The phone enters a name; it appears on the TV and the QR moves on to
  the next slot until 20 are in. A 21st phone is told the room is full
- **Ready**: each phone's waiting screen has READY (`tvReady`, tap again to
  undo). When everyone in is ready (2+ players), the server tells the TV
  (`tvAutoStart`) and it starts - nobody touches the computer. Alone in the
  room, the phone also shows PLAY SOLO. The TV's Start Game button still works
  (START SOLO with one player)
- **Show my game on this phone**: each player's own choice, on their phone -
  SHOW MY GAME ON THIS PHONE on the waiting screen, and a BOARD switch at the
  top of the controller to flip it mid-game (`tvShowGame`; the phone
  remembers it). On, the TV sends that player a picture of their own board
  (`Board.snapshot()`: one character per cell, next pill, held pill, score,
  viruses, level, target; the sprite list is `SPRITE_CODES` in components.js
  and repeated in controller.html) and the phone draws it on a canvas above
  the buttons. With 5+ players (CPUs count: the TV boards get small) it is on
  for everyone and the switches are locked (`boardForced`). Pictures are sent
  only when they change, up to 20 a second, over the direct link when there
  is one (else `tvState`)
- **Junk you can see coming** (every mode with attacks): an attack's virus shows at once, see-through and
  blinking, in the top row where it will start (`Board.previewJunk`, `junkQueue`; on a phone's own board via
  `j` in the snapshot). When the next pill is thrown the first one in the queue becomes real and drops, in
  that column unless it has filled up. It has the colour of the pill that was cleared to send it, and so do
  the ATTACK / INCOMING effects (attackFx.js `PILL_COLORS`)
- **Big rooms (9 to 20 players)**: the lobby switches to small slots in a wider
  panel with a smaller QR code (`.tv-slots.crowded`), and from 9 boards the name
  tags grow and leave out the target, which the phones still show (`body.tv-many`,
  `TAG_H_MANY`). As players go out the boards spread out and the tags shrink back
- **CPU players**: ADD CPU PLAYER on the TV lobby adds a computer player in the
  next empty slot - CPU #1, CPU #2... (the lowest free number) - and ✕ on its
  slot takes it out (`tvAddCpu` / `tvRemoveCpu`). A CPU is always ready (so one
  phone + CPUs starts as soon as the phone presses READY; with only CPUs, START
  GAME on the TV) and always wants a rematch. The TV page plays its board
  (`scripts/cpuPlayer.js`): for each pill it scores every place it can land
  (colours lined up, 4 in a row best, viruses in it better still; minus
  burying another colour and stacking high) and walks the pill there a move
  at a time through `movementFromKey`, at its own speed (140-230 ms a move)
  and sometimes taking a worse place, so CPUs differ and can be beaten. They
  attack and get junk like anyone. A 🤖 shows on their name tag
- **Playing**: every board runs on the TV page (`isTVControlled` games, made by
  tvHost.js directly - not script.js). Phone buttons move that player's pill;
  held buttons repeat. Each player keeps their own place in the shared pill
  list (`window.tvColorPositions`), so everyone gets the same pills. The
  computer keyboard does nothing in this mode
- **Targets and junk**: each player attacks the next player still in, round the
  circle (`tvHost.targets`, shown as "▸ name" on the TV and on the phone once 3+
  are in). A clear of 4+ calls `tvHost.sendAttack`, which gives the target junk
  on the TV page itself (`PlayingBoard.receiveDamage`) - TV boards do not use
  the server's p1damage/p2damage events
- **How junk works** (all modes): each attack is one junk, up to MAX_JUNK (4)
  waiting; each new pill brings one in (ThrowingBoard frame 0). It drops into
  a column with room at the top and falls all the way - fast - before the
  pill comes into play. It lands as a virus that counts towards clearing the
  board, but unlike the board's own viruses it falls again if what it sits on
  is cleared (`junkVirus`, `useGravitation`)
- **Teams match**: FREE FOR ALL / 👥 TEAMS on the TV lobby, with 2-8 teams
  named by colour - RED, BLUE, GREEN, YELLOW, PURPLE, ORANGE, TEAL, PINK
  (`TEAMS`, the same list in tvHost.js, controller.html and replays.html).
  Phones pick a team on the waiting screen (PICK YOUR TEAM) and can't press
  READY until they have; CPUs go on the smallest team and the TV can click a
  CPU's team chip to move it; anyone still without a team at the start joins
  the smallest (`tvBalanceTeams`). With fewer than two teams in the game it's
  everyone for themselves. Players attack the next player round the circle on
  another team; a team is out when all its players are; the last team
  standing, or the first to clear a board, wins (`tvGameOver` team, `tvResult`
  team / myTeam). Boards get a frame and name-tag chip in their team colour.
  Events: tvSetTeams, tvPickTeam, tvSetCpuTeam
- **Out**: a bottle that fills up is out (`tvEliminated`): the board greys,
  shows "OUT #place", then leaves the TV and the rest re-flow to fill the
  screen. That phone shows YOU'RE OUT and its place. Targets are reassigned;
  with two left they attack each other
- **Layout**: `tvHost.layout()` tries every split into rows and picks the one
  with the biggest boards - but a split with more rows wins when it's within
  4% (`STACK_BIAS`), so three players are two on top and one below rather than
  one long strip. Gaps and name tags are kept small (TAG_H, GAP, EDGE) so the
  boards get the room. On a 16:9 TV in fullscreen, three boards stacked are
  about 30% bigger than in a row; in a short, wide window the two are about
  the same size
- **Winning**: clearing all your viruses wins outright; otherwise the last one
  left wins (`tvHost.playerFinished`). The TV freezes the boards and shows the
  winner in a box you can drag aside (mouse or touch) to see the final boards
  behind it (`makeDraggable`); each phone gets `tvResult` (victory, or game
  over with the winner and your place)
- **Solo**: like single player - a cleared board shows STAGE CLEAR and the next
  level starts by itself (`tvNextLevel` -> `tvLevelData`, score kept); a full
  bottle is game over with the level and score
- **Hold**: a HOLD button above the phone's controls (and on the regular mobile
  controls, and the C key). It puts the falling pill in the hold box and brings
  in the next one, or swaps with the held pill (`PlayingBoard.hold()`). Once
  per pill: it comes back when the next pill is thrown in. The held pill shows
  on the phone's button and in a HOLD box on the board, over "SPEED LOW"
- **Rematch / Restart**: each phone's result screen has REMATCH (PLAY AGAIN
  solo). When everyone still in the room has asked, the server starts the next
  round (`startTvRound`); the TV shows who has asked. Pressing A on your own
  controller there is the same as REMATCH (`tvRematchFor`, from the TV). The
  TV's RESTART does the same at once. EXIT reloads to the menu, which closes
  the room
- **Pause**: + or - on a controller, ⏸ at the top of a phone (the `pause`
  action through tvInput / the direct link) or PAUSE at the bottom left of the
  TV pauses every board for everyone; any of them resumes. `setPaused` in
  tvHost.js sets `window.gamePaused`, and Board.nextFrame, the throwing board,
  gravity, movementFromKey and the CPUs skip their ticks while it's on. Held
  buttons are let go and other presses are ignored (input-ignored "paused").
  Phones get `paused` in their state, dim their pad and show ▶. The TV shows
  "⏸ PAUSED BY NAME". Logged as `paused` / `resumed`. A new round or the
  end of the match always unpauses
- **Held drop**: a held DROP (phone, controller or keyboard) only drops the
  pill it was pressed for. When that pill lands, the repeat stops until DROP is
  pressed again, so a press made while junk falls never sends the next pill
  straight down. The fast junk drop (`fastDamageDropInterval`) stops as soon
  as there's a pill, so it never moves one
- **Fullscreen**: ⛶ FULLSCREEN at the bottom right of the TV (lobby and game).
  Every try is logged (`fullscreen-click`, `fullscreen-change`,
  `fullscreen-error` with the browser's reason, `fullscreen-no-change` when
  nothing happened, with whether the click counted as a user gesture), and a
  tip offers F11 when the browser says no
- **Anywhere, not just this computer**: on the public site anyone can open a
  TV Room. Each phone opens a WebRTC data channel straight to the TV page
  (`tvSignal` carries only the set-up; STUN: stun.l.google.com), so presses
  and board pictures go over their own Wi-Fi. The phone shows "⚡ DIRECT" and
  the TV a ⚡ by the name. If the channel can't open, everything goes through
  the server automatically
- **Phone or controller**: on the waiting screen each phone picks PLAY WITH
  📱 PHONE or 🎮 CONTROLLER (`tvChooseInput`; the phone remembers it). A
  CONTROLLER player gets a game controller on the TV computer: pressing A on a
  free one gives it to them (the player who has waited longest, if several
  are waiting), or they tap it in the list on their phone
  (`tvPickController`, which the TV decides). In the lobby, pressing A on
  your own controller - including the press that claims it - counts as READY
  (`tvReadyFor`; the phone's READY button shows it and can still undo it).
  The TV tells the phones which controllers it has and whose they are
  (`tvControllers`); a Pro Controller's lamps light up with its player number
  (`padInput.showPlayer`). Everyone can have their own controller. The TV
  lobby slot shows 📱, or a solid badge in the player's colour with the
  controller's name (a flashing dashed "PRESS A" while waiting); the board's
  name tag carries the same badge; a banner across the top of the TV says
  "🎮 PRO CONTROLLER 2 ▸ NAME" when one is paired and "NAME'S CONTROLLER
  DISCONNECTED" when one goes,
  and the phone shows whose controller it is instead of the buttons (with
  USE MY PHONE INSTEAD). The TV reads all controllers at once
  (`padInput.watchAll`) and passes each one's presses to handleInput, like a
  phone's. Switching back to the phone, or leaving, frees the controller; it
  works mid-game too. In Chrome the lobby has CONNECT CONTROLLER (WebHID), as
  in single player - once per Pro Controller. Not in single player's PHONE
  room
- **Copy link**: under the QR code, for a player who can't scan it
- **Attack effect**: `scripts/attackFx.js` - "ATTACK!" and a shockwave on the
  attacker, a comet to the target (`attackSent(player, target)`,
  `attackReceived(player, from)`), a red flash, shake and "INCOMING!" when it
  lands; the phones flash too (`tvFx`). Also used by AI mode and online rooms.
  A failure inside an effect is caught (it must never stop the game) and logged
  with console.warn - once, a broken effect hid silently behind that catch
- **Phones that sleep**: a phone keeps an id in localStorage and gets its slot
  back when it reconnects. In the lobby a disconnected slot can be taken
- **Server events**: tvCreateRoom, tvJoin, tvReady, tvStartGame, tvInput,
  tvState, tvEliminated, tvNextLevel, tvGameOver, tvFx, tvRestart, tvRematch,
  tvSignal, tvChooseInput, tvPickController, tvControllers, tvShowGame,
  tvAddCpu, tvRemoveCpu, tvReadyFor, tvRematchFor (in);
  tvRoomCreated, tvLobby (TV and phones), tvAutoStart, tvJoined, tvJoinError,
  tvGameStarted, tvInput, tvState, tvEliminated, tvLevelData, tvResult, tvFx,
  tvRematch, tvSignal, tvRoomClosed, tvPickController, tvControllers (out). QR
  images come from `GET /tv/qr.svg?text=`

SINGLE PLAYER: KEYBOARD, PHONE OR PRO CONTROLLER
------------------------------------------------
SINGLE PLAYER first asks how you want to play (`#controlPicker` in index.html;
arrow keys move between the choices, Escape goes back):

- **Keyboard** (TOUCH on a phone-sized screen): the single player game as
  before (`startSinglePlayer`)
- **Phone**: a TV Room for one phone (`tvHost.startPhoneSolo()`,
  `tvCreateRoom({ solo: true })` - the room has `soloOnly`). The lobby shows
  only the QR code; its link has `&solo=1`, so controller.html skips the name
  and READY screens and joins at once (saved name, else "PLAYER 1"). The
  server starts the game as soon as the phone is in (`tvAutoStart`) and turns
  away a second phone. From there it is the TV Room's solo game: STAGE CLEAR
  goes on to the next level, PLAY AGAIN on the phone, ⚡ direct link, etc.
- **Pro Controller**: `scripts/gamepad.js` (`window.padInput`). The connect
  screen (`#padConnect`) explains Bluetooth pairing and waits for the browser
  to see a controller - browsers only show one after a button is pressed -
  then A or + (or START) begins the regular single player game. Buttons become
  the same key presses as the keyboard (keydown when pressed, keyup when let
  go), so held buttons repeat like held keys and "press any key" screens work.
  By the letters on the buttons: D-pad / left stick move (down = drop), A and
  X rotate right, B and Y rotate left, L R ZL ZR hold. Browsers number the
  face buttons differently - Chrome (and the WebHID reader) by position, B at
  the bottom = 0; Safari by letter, A = 0 (`faceButtons()`). Rotate and hold
  happen once per press (a held key repeats every 166 ms in Board.js, which
  made a slightly long press turn the pill back a split second later); moving
  and dropping repeat while held. While a message is up
  (GAME OVER), A or + presses its button instead, after one second so mashing
  A doesn't hit EXIT. Polling runs on requestAnimationFrame, only while
  playing or while the connect screen is open
- **Chrome on a Mac**: Chrome reads Nintendo controllers itself instead of
  through macOS, and misses a Pro Controller paired over Bluetooth (Safari
  sees it; tested on macOS 15.6 with a genuine controller, 057e:2009). So the
  connect screen has CONNECT CONTROLLER (Chrome and Edge, WebHID): the player
  picks the controller in Chrome's list, and gamepad.js opens it, asks for
  full reports (subcommand 0x03 0x30), lights the player 1 lamp (0x30 0x01)
  and reads report 0x30 (buttons + 12-bit sticks) into a stand-in standard
  Gamepad. Chrome remembers the choice: after a reload or a reconnect the
  controller is opened again by itself (`navigator.hid.getDevices()` and the
  `connect` event)
- **EXIT** after a single player game reloads to the menu: a second game on
  the same page used to get a dead board

GAME LOGS (TRACKING DOWN GLITCHES)
----------------------------------
Every game is written down in detail so a glitch can be traced afterwards - see
CLAUDE.md for how to read them (`node tools/gamelog.js`).

- **Where**: `logs/games/<id>.jsonl` (not in git), the last 100 games. One file
  per single player game, AI or online game, and per TV Room round (lobby
  events before the first round go at its top). Ids start with the date
  (20261028-153012-tv-abcd-k3f) and show on the result screens ("Game log: …")
- **Who writes**: the server (`gameLogs.js`: batched, 25 MB cap per game) from
  three sources - the page (`public/scripts/gameLog.js`), each phone
  (`controller.html`, `plog`), and the server itself (every event each socket
  sends and gets, lobby changes, auto start, disconnects)
- **What**: gameLog.js wraps the game's own methods, so every move and what it
  did, each pill, clear, junk, hold, stage clear and top-out is written without
  touching the game code; each board once a second while it changes; errors,
  console warnings, slow frames (`hitch`), long tasks, socket drops, ping. The
  TV adds inputs with where they came from (`via`) and why one was ignored,
  attacks, eliminations, layout, controllers, CPU decisions. Phones add button
  presses (direct or through the server), the direct link, sleeping
- **🐞**: a button in the corner while a game is on (and on each phone's pad)
  marks "something looked wrong here", with every board as it is right then.
  Marks also go in `logs/markers.jsonl`; a phone's mark shows a banner on the TV
- **Replays**: `replays.html` (🎬 REPLAYS on the menu, or /replays) lists the
  last 100 games (`/logs/list.json`, summaries kept in logs/index.json) and
  plays any of them back: every board rebuilt from the frames gameLog.js
  writes (a full picture every 2 s, the changed cells every 50 ms, score /
  viruses / next / hold), with play, pause, ¼×-8× speed, a scrub bar marked
  with 🐞 / errors / eliminations, step by step (← →), and a feed of what
  happened (attacks, clears, inputs, problems) - click one to jump there
- **Reading**: `/logs` and `/logs/<id>` from this computer or its Wi-Fi (a
  request through a proxy - a hosted server - only with `?key=` matching the
  LOG_KEY environment variable), or the reader: `node tools/gamelog.js summary
  latest`, `around latest marker`, `board latest marker`, and `audit latest`,
  which looks for glitches by itself: pieces hanging in mid-air with nothing
  falling (junk viruses too), a virus counter that disagrees with the board, a
  pill stuck or teleporting or coming in away from the spawn spot or onto a
  virus, junk that never dropped, slow pills, a "cleared" win with viruses
  left, errors and freezes
- **Found this way** (8-CPU games, audited, fixed): the server dealt the same
  virus cell twice and never used column 7 (its random numbers broke past
  2^53 - now `seededRandom`, mulberry32); a cleared cell's pop timer blanked a
  piece that had just fallen into it (an invisible block pills landed on);
  junk fell while the next pill was already in play (junk froze in mid-air on
  top of the pill); gravity stopped after a chain clear (pieces left floating);
  two attacks before your next pill counted as one; junk stayed in mid-air
  when what it landed on was cleared; junk dropped into a full column landed
  on top of a virus (which vanished but still counted)

PLAYER STATS
------------
`/stats` (`public/stats.html`) shows who is online and in which game, players per
day (new and returning), how many come back, games by mode, where players came
from and the latest players. It reads `/stats.json`, with the same access as the
game logs: this computer, its Wi-Fi, or the owner's key. The code holds only its
hash (`OWNER_KEY_HASH` in server.js), so nothing has to be set on the host; `LOG_KEY`
works as well if it is set. The private link puts the key after a #, so it stays out
of server logs, and the page then keeps it on that device.

- Every page runs `scripts/hello.js`: a random id kept in the browser's
  localStorage, where it came from (`?ref=` or `utm_source` on the link, an invite,
  the TV's QR code, or the referring site), phone or computer, and language. No IP
  addresses, cookies or third parties. The rules say so.
- `analytics.js` counts a visitor when a page says hello and a player when they
  start a game (`logOpen`, or `startTvRound` for each phone). CPUs never count, not
  even Free Play's with real names. One person on two devices counts twice.
- Opening `/stats` turns off counting on that device (`statsIgnore`; a switch on the
  page turns it back on), so the owner's own games don't inflate the numbers.
- The numbers are saved to `analytics.json` beside the logs every 30 s and when the
  server stops. Render wipes that file on every restart, so the owner's Mac keeps a
  private copy: `tools/stats-keeper.sh`, run every 10 minutes by launchd (the owner
  installs it once with `tools/install-stats-keeper.sh`), takes
  `/stats/backup.json` with the owner's key and sends its copy to `/stats/restore`
  when the server says it started with nothing. It only works while the Mac is on; a
  restart can lose what happened since the last copy. A persistent disk (`LOG_DIR`)
  would close that gap.
- Its request also wakes the server, so while the Mac is on a new player is less
  likely to wait for a server that fell asleep.

RUNNING IT FOR REAL (PRODUCTION / RENDER)
-----------------------------------------
Measured on this Mac with 300 simulated players (50 rooms of 6, every board
sending 5 updates a second, attacks every 3 s, plus their game logs): 7,400
board updates delivered a second, delivered in 7 ms (99% within 16 ms), the
server at about 13% of one core and 175 MB. What makes that possible:

- **Network**: pages connect with WebSocket straight away (falling back to
  long-polling if a network blocks it) and load Socket.IO from this server
  (the same version as the server; it used to come from a CDN, version 4.0.0).
  Socket messages aren't compressed one by one (perMessageDeflate off: they're
  tiny), the largest accepted is 512 KB, and each socket has per-second limits
  per message type (RATE_LIMITS) so one client can't flood the server
- **Only to who needs it**: attacks in the old online rooms and AI mode used
  to go to every connected player (io.emit); they now go to the room. Board
  pictures in a party are diffs (a few cells), not whole boards
- **Static files**: HTML, scripts and styles are brotli/gzip-compressed once
  and kept in memory (the menu page: 108 KB -> 18 KB), with ETags (a return
  visit is a 304) and checked on every visit so a deploy shows up at once;
  images cache for a week. `/healthz` answers instantly (point Render's health
  check at it)
- **Quiet**: the server no longer prints the virus and pill lists on every
  game (25 debug lines -> 1), and on the live site pages drop console.log
  (warnings and errors stay; add ?debug to the address to see everything)
- **Memory**: finished rooms, TV rooms and parties are forgotten along with
  their game data (they used to stay in memory for as long as the server ran);
  a destroyed board removes its key listeners (they used to pile up with every
  level)
- **Game logs on the live site**: written in the background (never blocking
  the server), replay frames at 10 a second instead of 20, and the server's
  own note of every socket message is off (LOG_VERBOSE=1 turns it on).
  Render's disk is wiped on every deploy: set LOG_DIR to a persistent disk to
  keep them. Reading them there needs LOG_KEY (e.g. /replays?key=... - the
  list and logs check it; requests through Render's proxy are never "local")
- **Settings** (environment): PORT (Render sets it), RENDER / NODE_ENV=
  production (production mode), LOG_DIR, LOG_KEY, LOG_VERBOSE
- **Size**: one server process handles hundreds of players. Render's free
  instance has a tenth of a CPU and sleeps when idle - use at least a Starter
  instance for real traffic. For thousands at once, run several instances with
  the Socket.IO Redis adapter and sticky sessions

KEEPING IT SMOOTH
-----------------
Measured with two boards on a 1920x1080 page: the old animated background
(`background-position` on a 400% gradient) made the browser re-rasterize the
screen every frame - about 1.4 s of raster work per second, which showed up as
stutter. It is now two fixed gradients with the top one fading (opacity only):
about 10 ms per second. Rules that follow from it:
- Animate only `transform` and `opacity`. Animating backgrounds, filters,
  box-shadows or sizes repaints every frame
- Decorative animations that repaint (the logo glow) stop while a game is on
  screen (`body.in-game`)

GAME MECHANICS
==============

PILL SYSTEM
-----------
- **Structure**: Two-colored capsules that fall from top
- **Movement**: Left/right movement, rotation in 4 directions
- **Colors**: Blue, Brown, Yellow (3 possible colors)
- **Matching**: 3+ same colors in row/column clears them
- **Synchronization**: Both players get identical pill sequences

VIRUS SYSTEM
------------
- **Structure**: Single-colored targets that must be eliminated
- **Spawning**: Placed at game start in synchronized positions
- **Elimination**: Cleared by matching their color with pills
- **Animation**: Dancing viruses around board perimeter
- **Synchronization**: Identical virus positions for all players

SCORING SYSTEM
--------------
- **Virus Elimination**: Points for clearing viruses
- **Line Clears**: Bonus points for clearing multiple lines
- **High Scores**: Persistent storage with localStorage
- **Multiplayer**: Real-time score synchronization

DAMAGE SYSTEM
-------------
- **Trigger**: Clearing lines sends damage to opponent
- **Visual**: Falling colored pieces from top of opponent's board
- **Effect**: Pieces become viruses when they land
- **Strategy**: Creates competitive pressure and strategic depth
